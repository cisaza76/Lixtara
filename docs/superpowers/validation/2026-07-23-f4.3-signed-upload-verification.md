# F4.3 — Supabase signed-upload technical verification

- **Date:** 2026-07-23
- **Purpose:** confirm the F4.3 direct-to-Storage upload (`source-video-section.tsx`'s XHR PUT to
  the signed URL) is protocol-correct against Supabase Storage, and document any limitation.
- **Evidence base:** the installed SDK source `@supabase/storage-js@2.105.4`
  (`dist/index.mjs`) + the project's existing browser-direct upload (`photo-uploader.tsx`).

## What the component does (F4.3)

`/initiate` calls `storage.createSignedUploadUrl(path)` → `{ signedUrl, token }`. The component
then does an **XHR `PUT` to `signedUrl`** with the raw `File` body, headers `content-type:
<file.type>` + `x-upsert: false`, `xhr.upload.onprogress` for progress, and `xhr.abort()` wired to
an `AbortController`.

## Verification (against the real SDK)

| Requirement | Finding | Verdict |
|---|---|---|
| **PUT** | `uploadToSignedUrl` calls the `put` helper → `_handleRequest(fetcher, "PUT", …)`. The signed-upload endpoint is a **PUT**. | ✅ matches |
| **URL** | `createSignedUploadUrl` returns `signedUrl = ${storageUrl}/object/upload/sign/${path}?token=${token}` — a full absolute URL with the token embedded. XHR `PUT signedUrl` targets the exact endpoint the SDK uses. | ✅ directly usable |
| **Content-Type** | For a non-FormData body the SDK sets `content-type: options.contentType` (+ `cache-control`). The component sets `content-type: file.type`. | ✅ present (see limitation) |
| **XHR progress** | `xhr.upload.onprogress` fires for a PUT with a body (raw or multipart). Not simulated. | ✅ supported |
| **AbortController** | `xhr.abort()` on `signal.abort` cancels the in-flight PUT (rejects with `AbortError`); the flow treats it as `aborted` and keeps the prior source. | ✅ supported |
| **CORS / preflight OPTIONS** | A cross-origin PUT with custom headers triggers a preflight OPTIONS. The repo already uses the browser-direct upload pattern (`photo-uploader.tsx` → `supabase.storage.from(bucket).upload(...)`), which is design-compatible with the signed-URL PUT (same storage origin, same preflight-triggering headers). This is NOT, however, a runtime CORS proof for the project/domain/bucket as currently configured. | ⚠️ Compatible by design and backed by the repo's existing pattern; **pending runtime confirmation in a browser against the configured project + bucket.** |

## Documented limitation (one)

**Body encoding: raw file vs. the SDK's FormData-for-Blob.** For a browser `Blob`/`File`, the SDK's
`uploadToSignedUrl` sends **`multipart/form-data`** (a `FormData` with a `cacheControl` field + the
file appended as `""`), NOT a raw body. The F4.3 component sends the **raw `File`** with a
`content-type` header — which is the SDK's *else* branch (used for `ArrayBuffer`/stream bodies) and
is a supported server code path, so it is expected to work. However, the sanctioned browser default
is FormData.

- **Risk:** low. The endpoint accepts raw-body PUTs (the SDK's own else branch relies on it), and
  CORS/PUT/URL/content-type are all satisfied.
- **If the raw PUT is ever rejected by the endpoint** (e.g. it requires the `cacheControl` form
  field for browser uploads), the fix is a **small, localized change** to the component's
  `putSignedUrl`: build a `FormData`, `append("cacheControl", "3600")` and `append("", file)`, and
  PUT that instead — `xhr.upload.onprogress` and `abort()` work identically on a FormData body.
- **Must NOT be changed preemptively.** Do not switch the component to `FormData` without runtime
  evidence of a raw-PUT failure — the raw path is a supported SDK code branch and switching blindly
  would be unjustified churn. The FormData variant is a documented **fallback**, applied only if a
  real-browser upload actually fails.
- **Runtime confirmation item** (run once the feature is enabled: flag ON + bucket created): upload
  a real MP4 via the UI against the configured project/bucket and confirm a 200 + progress; only if
  it fails, apply the FormData fallback above.

## Conclusion

The F4.3 signed-upload approach is protocol-correct: **PUT**, **token-embedded absolute URL**,
**Content-Type**, **real XHR progress**, and **AbortController cancel** are all confirmed against the
SDK. **CORS** is compatible by design and backed by the repo's existing browser-direct upload
pattern, but is **pending runtime confirmation** in a browser against the configured project +
bucket. The raw-file body is also **pending runtime confirmation** (with a documented FormData
fallback that must NOT be applied preemptively). No architecture or contract change is required; the
two open items are runtime confirmations, not code changes.
