# F4.6 — Asset Archive · Design (analysis only, no code)

- **Status:** DESIGN — not implemented, not authorized to implement.
- **Date:** 2026-07-23
- **Related:** ADR-0009 (retention & cleanup), F4.5 dry-run engine (`source-retention.ts`),
  the resolve-video-source canonical authority, ADR-0007 (replacement).
- **Scope:** soft-archive of **Source Video** Assets (`kind=video, source_type=seller_upload`)
  without physical deletion and without changing the current-source authority.

## Binding principle (from ADR-0009)

```text
resolveVideoSource is the only authority that decides which Source Video is current.
Archive: consults it → never archives the current → applies lifecycle decisions only to
non-current Assets → never recomputes or replaces the current selection.
```

### Archive makes no decisions (executor discipline)

```text
Archive never makes decisions.
The executor only executes the plan produced by computeRetention.
It does NOT recompute current.
It does NOT re-order.
It does NOT apply heuristics.
It does NOT generate candidates.
```

The executor's entire input is the F4.5 plan (`computeListingRetention` output: `{ current,
retained, orphans }` per listing). It archives exactly the `orphans` it is handed, guarding each
write with the `current` id from that same plan. All selection/ordering/candidate logic stays in
the already-tested pure engine; the write layer is mechanical.

## 2. Proposed architecture

A new **domain service** (write layer) that consumes the F4.5 classification and performs an
atomic, guarded, audited lifecycle flip — leaving `AssetStore` insert-only and
`resolveVideoSource` untouched.

```
F4.5 engine (pure, read-only)                    NEW in F4.6
─────────────────────────────                    ──────────────────────────────────────────
resolveVideoSource (authority) ──current──▶  SourceArchiveService (src/lib/creative-studio/source-archive.ts)
computeListingRetention ────────orphans──▶     ├─ archiveAsset(cmd)   ← primitive (one atomic op)
                                               └─ archiveAssets(cmds) ← batch = loop, per-asset result
                                                        │
                                                        ▼  narrow port
                                                ArchiveWriter.archive(cmd)  (one method)
                                                        │
                                                        ▼  Supabase impl (service client)
                                                conditional UPDATE (guarded, atomic, RLS-bypassing)
                                                  + idempotent audit insert into activity_log
                                                  [RPC = documented upgrade path only if needed]
```

- **Separation:** archive lives in its own module + narrow port; `AssetStore` stays insert-only
  (its immutability comment remains true). resolveVideoSource and the retention engine are
  consumed, never modified for selection.
- **Entry point (F4.6):** a **runner script** (`scripts/archive-source-retention.ts`), analogous
  to the dry-run runner, invoked manually under owner sign-off. **Not** cron, **not** an endpoint,
  **not** UI (all out of scope). Gated by a feature flag + a `--apply` opt-in (default = dry-run
  passthrough).

## 3. Lifecycle transition model

- **Valid transition:** `active → archived`, where **active = any lifecycle except `archived`**
  (`draft | ready_for_review | approved | rejected`). For Source Videos in scope, this is in
  practice `draft → archived` (sources are created `draft`).
- **`archived` already exists** at CHECK + enum level — nothing to add there.
- **Archivable states:** any non-`archived` lifecycle, **restricted** to the F4.5-classified
  Source Video orphan set. The primitive guards generically (`lifecycle <> 'archived'`); the
  candidate set is what constrains it to Source Videos.
- **Rejected transitions:**
  - archiving the **current** → refused by the guard (`id <> currentId`) → outcome
    `skipped_current` (and logged loudly — under §4's invariant this should never occur).
  - archiving an **already-archived** asset → no-op → outcome `already_archived` (idempotent, not
    an error).
- **Restoration path:** `archived → prev_lifecycle`. **Restoration is BACKLOG** (documented future,
  not F4.6). F4.6 makes it *possible* by capturing `prev_lifecycle` in the audit (§5), so a future
  restore is a pure data operation with no guesswork. F4.6 implements archive only.

## 4. Concurrency & atomicity (the critical part)

### Structural safety argument (why the current is provably protected)
Invariants in F4.6 scope: **(I1)** assets are append-only — no delete, no bytes mutation;
**(I2)** `resolveVideoSource` selects newest-by-`created_at` eligible with **no lifecycle filter**
(unchanged in F4.6); **(I3)** F4.6 archive only ever targets assets the F4.5 engine classified as
**non-current** (orphans), where `current` came from `resolveVideoSource`.

> **Claim:** an orphan can never become the current later, so archiving it can never remove the
> real current. **Proof:** an orphan X has a strictly newer eligible asset (the current C, or a
> newer one). New uploads only add assets with even greater `created_at`; `created_at` is immutable
> (I1). So the max-`created_at` eligible is always some asset ≠ X. By I2, `resolveVideoSource`
> always returns that max — never X. ∎

The current is therefore protected *structurally*, independent of timing. But the requirement
"no uncontrolled read→decide→update window" demands an **atomic guard at write time** anyway
(defense-in-depth + future-proofing).

### The atomic primitive (guarded conditional UPDATE — no RPC unless proven necessary)

**Decision (owner, 2026-07-23):** design with a plain **conditional UPDATE from the service
client** first. Do **not** introduce a SECURITY DEFINER RPC until implementation surfaces a real
atomicity/consistency limitation that cannot be solved elegantly at the app layer.

The primitive is a single guarded UPDATE (expressible directly in supabase-js):

```sql
update public.assets
   set lifecycle = 'archived', archived_at = now()
 where id = :assetId
   and owner_id = :ownerId          -- owner-scoped
   and id <> :currentId             -- current-protection; authority-supplied, NEVER reselected here
   and lifecycle <> 'archived'      -- idempotency
 returning id;                      -- 1 row = flipped, 0 rows = nothing changed
```
```
supabase-js: .from("assets").update({lifecycle:"archived", archived_at:<now>})
  .eq("id",assetId).eq("owner_id",ownerId).neq("id",currentId).neq("lifecycle","archived").select("id")
```

- **The safety-critical guard is atomic without an RPC:** a single-row UPDATE is atomic in Postgres.
  Two concurrent UPDATEs row-lock — the first flips, the second sees `lifecycle='archived'` → 0 rows.
  So *current-protection* and *idempotency* are already atomic at the app layer.
- **No reselection:** `:currentId` comes from the plan (`resolveVideoSource`); the SQL never
  recomputes currency — honors the "archive makes no decisions" principle.
- **`prevLifecycle` needs no re-read:** the executor already holds the classified Asset (from the
  F4.5 plan / `listByListing`), so it knows the orphan's lifecycle and passes it to the audit — no
  `read → decide → update`.
- **Window minimization:** the batch re-resolves `current` per listing immediately before archiving
  that listing's orphans, and passes that fresh id into each UPDATE.

### Where the conditional UPDATE is NOT single-transaction — and why that is acceptable here

The one place the app-layer approach is *not* one transaction is the **state flip (UPDATE) vs. the
audit insert (a second statement into `activity_log`)**. A process crash between them could leave an
archived asset with no audit row. This is the only real atomicity gap — and for F4.6's scope it is
bounded and resolvable elegantly, so **it does not justify an RPC yet**:

1. **The safety-critical property is already atomic.** Never-archive-current and idempotency live
   entirely in the single UPDATE. The audit is *evidence*, not a guard — its loss never corrupts
   selection or archives the wrong asset.
2. **`prevLifecycle` is recoverable by construction.** For `seller_upload` sources, lifecycle is
   `'draft'` at creation and there is **no code path that mutates an Asset's lifecycle** (AssetStore
   is insert-only). So a Source Video's `prevLifecycle` is invariantly `'draft'` — a lost audit does
   not lose the restore target.
3. **The audit is idempotently re-ensurable** (the F4.1 `ensure…Audit` find-or-insert pattern +
   the existing partial-unique index style on `activity_log`): a re-run can re-emit the missing
   audit event. Combined with (2), the restore target survives even the crash case.

**Conclusion:** the conditional UPDATE from the service client is sufficient for F4.6. **The RPC
remains a documented upgrade path** — to be adopted only if a future scope breaks assumption (2)
(a non-constant `prevLifecycle`) or a hard requirement demands single-transaction state+audit. This
is recorded so the escalation is deliberate, not incidental.

### Idempotency / edge outcomes (also §3)
The plan guarantees each target existed, was owner-matched, and was non-current at classification.
Under those guarantees a **0-row** UPDATE result unambiguously means "raced → already archived";
no pre-read is needed to decide (an optional `getById` may refine the log label only).

| Situation | Outcome |
|---|---|
| flip succeeds | `archived` (audit emitted; `prevLifecycle` from the plan) |
| already archived (or raced) | `already_archived` (0 rows; no duplicate audit) |
| asset does not exist | `not_found_or_not_owner` (0 rows) |
| asset belongs to another owner | `not_found_or_not_owner` (0 rows; owner guard) |
| asset **is** current | never reaches the write (engine never emits current as an orphan); if forced, guard `id <> current` → 0 rows → logged as an invariant alarm |
| two processes archive simultaneously | one `archived`, one `already_archived` (row lock) |
| current changed between eval and write | orphan still archived (invariant §4); stale `currentId` harmless — target ≠ current regardless |

> **Recommendation #3 (updated):** **conditional UPDATE from the service client** (atomic guard +
> idempotency at the row level). An RPC is **not** introduced now; it is the documented escalation
> if a real atomicity/consistency limitation is demonstrated during implementation.

## 5. Audit strategy

Emitted **only** on an actual flip (idempotent re-runs write nothing). Two stores:
- **On `assets` (denormalized):** `archived_at timestamptz` — set atomically with the flip. Needed
  for future GC-by-age and fast `archived_at is not null` filtering. `lifecycle='archived'` is the
  state; `archived_at` is the when.
- **Append-only audit event** (recommend reusing `activity_log`, action_type
  `creative_studio.source_asset_archived`), one row per successful archive.

| Field | Mandatory? | Purpose |
|---|---|---|
| `assetId` | ✅ | subject |
| `archived_at` | ✅ | when (GC-by-age, correlation) |
| `prevLifecycle` | ✅ | **reversibility** (restore target) |
| `actor` / `source` | ✅ | who/what did it (`retention_batch`, later `user_delete`) |
| `runId` | ✅ | correlation dry-run report ↔ execution ↔ audit ↔ logs |
| `reason` | ✅ | why (retention policy K, user request) |
| `listingId`, `ownerId` | ⬜ optional | denormalized for querying |
| `bytes`, dry-run report hash | ⬜ optional | reclaim accounting / integrity link |

> **Recommendation #4 (imprescindibles):** `assetId, archived_at, prevLifecycle, actor/source,
> runId, reason`. **Sink = `activity_log`** (owner-decided 2026-07-23) — action_type
> `creative_studio.source_asset_archived`, payload in `metadata` jsonb; idempotent find-or-insert
> (F4.1 pattern) + a partial-unique index on `(metadata->>'assetId')` for that action. No new table.

## 6. Integration with F4.5 (no duplicate logic)

The dry-run report **is** the archive plan. Execution reuses the **already-tested pure engine** for
classification and adds only the write step:

1. `current = resolveVideoSource(listing, owner)` (authority — same call the dry-run makes).
2. `computeListingRetention(key, current, listingAssets, K)` → `{ current, retained, orphans }`
   (the **same** F4.5 function; no second candidate-selection).
3. For each `orphan`: `archiveAsset({ assetId: orphan.id, ownerId, currentId: current.id, reason,
   runId })`.

No new selection/candidate code. The archive service is a **consumer** of the engine's output.

**One additive engine change (F4.6):** so re-runs don't keep reporting already-archived assets as
reclaimable, `computeListingRetention` gains an `alreadyArchived` bucket — it reads `lifecycle` only
to *separate already-handled assets from fresh orphans* (orthogonal to currency; does not touch the
selection authority). This keeps dry-run and execution consistent across repeated runs.

## 9. Risks

1. **A future `resolveVideoSource` change that filters `archived`** (F4.5 user-delete) could make
   archiving the *current* shift selection. Mitigation: F4.6 **never** archives the current; the
   guard + invariant hold regardless. Flagged for the user-delete sub-stage.
2. **Tiebreak mismatch:** `resolveVideoSource` orders by `createdAt` only; the F4.5 engine adds
   `id desc`. For equal `createdAt`, the "current" the authority picks could differ from the
   engine's ordering. Mitigation: the guard is `id <> current.id` (exact authority id), **not** a
   `createdAt` comparison — so archive is always safe. (Worth converging the tiebreak later;
   out of scope.)
3. **RLS**: archive works only via the service client. If ever invoked from an RLS-enforced client
   it silently updates 0 rows. Mitigation: the runner uses `createService()`; a test asserts the
   write path is service-role.
4. **Report/execution drift** if the DB changes between dry-run and apply. Mitigation: re-resolve
   current per listing at apply time; correlate via `runId`; alert on deviation (§9 obs).
5. **Idempotency of audit** under concurrency. Mitigation: single-flip guarantee + the
   partial-unique index (§8.2).
6. **State-flip vs. audit-insert not single-transaction** (the app-layer approach's only atomicity
   gap; see §4). Bounded and mitigated: the safety-critical guard is atomic in the UPDATE; a Source
   Video's `prevLifecycle` is invariantly `'draft'` (no lifecycle-mutation path exists), so a lost
   audit never loses the restore target; and the audit is idempotently re-ensurable. **No new
   blocking risk** — this is why an RPC is *not* introduced now (it stays the documented escalation).

## 10. Rollback

- **Code:** feature-flagged; disable the flag → archive service inert. Revert the new modules
  (additive; nothing else depends on them).
- **Migration:** `drop index assets_archived_at_idx; alter table assets drop column archived_at;
  drop function archive_source_asset; ` (+ drop audit index/table if added). Reversible; if run
  before any archive, zero rows affected.
- **Data (a bad archive run):** **fully reversible, no hard delete.** Restore SQL keyed by `runId`:
  `update public.assets a set lifecycle = e.prev_lifecycle, archived_at = null from (audit rows for
  :bad_run) e where a.id = e.asset_id and a.lifecycle = 'archived';` — possible precisely because
  `prev_lifecycle` + `runId` are captured (§5). Delivered as a rollback runbook.
- **No hard delete anywhere**, at any layer.

## 12. Recommended decisions

1. **Individual or batch?** → **Both.** `archiveAsset` is the atomic primitive; `archiveAssets` is
   a loop over it with **per-asset** results (see #6).
2. **`AssetStore` method or domain service?** → **Separate domain service** (`source-archive.ts`) +
   a narrow `ArchiveWriter` port. Keep `AssetStore` insert-only (its immutability stays true).
3. **Conditional UPDATE or RPC?** → **Conditional UPDATE from the service client first** (owner
   decision). The single guarded UPDATE makes current-protection + idempotency atomic at the row
   level; `currentId` is authority-supplied, never reselected. An RPC is the **documented escalation
   only if implementation proves a real atomicity/consistency limitation** (§4).
4. **Mandatory audit fields?** → `assetId, archived_at, prevLifecycle, actor/source, runId, reason`
   (optional: listingId, ownerId, bytes). **Sink = `activity_log`** (owner decision).
5. **Restoration now or backlog?** → **Backlog.** F4.6 captures `prevLifecycle` to make it possible;
   does not implement it.
6. **Batch atomic or per-asset result?** → **Per-asset result** (each op individually atomic); a
   partial failure never rolls back successful archives.
7. **How is the current protected against races?** → authority-supplied `currentId` guard
   (`id <> currentId`) inside the atomic conditional UPDATE, re-resolved per listing right before the
   write, backed by the structural invariant (append-only + newest-wins ⇒ an orphan can never become
   current).

## 14. Staged implementation outline (for when authorized — no code yet)

Each stage is small, tested, gated, and independently reviewable — the established F4.x cadence.

- **Stage A — Pure contracts** *(implemented 2026-07-23)*. `source-archive.ts` types:
  `ArchiveCommand`, `ArchiveOutcome`
  (`archived | already_archived | not_found_or_not_owner | skipped_current | error`),
  `ArchiveResult`, `ListingArchivePlan`, the `ArchiveWriter` port, and `archiveAssets`
  (loop over `archiveAsset`, per-asset results). **Error-handling responsibility:** the
  primitive `archiveAsset` is **transparent** — it propagates any `ArchiveWriter` exception; the
  **batch** `archiveAssets` is the layer that catches it, records an `"error"` result, and
  continues. Pure, fully unit-tested with a fake `ArchiveWriter`. No DB. Encodes the "executor
  makes no decisions" discipline.
- **Stage B — Engine `alreadyArchived` bucket** *(implemented 2026-07-23)*. Additive change to
  `computeListingRetention` so archived assets are separated from fresh orphans (reads `lifecycle`
  only; selection untouched); tests for consistency across re-runs. Implementation notes: archived
  assets are filtered out of the non-current remainder BEFORE the K-split (they do not consume
  retained slots); the injected `current` is trusted verbatim whatever its lifecycle (never lands
  in the bucket); `alreadyArchived: AssetRef[]` added to the resolved variant,
  `totals.assetsAlreadyArchived` to the report, and an "Already archived" line to the summary.
  Fixpoint test: archiving run-1's orphans yields orphans=[] on re-run.
  *Verified against the Stage B mandate 2026-07-25* — test suite extended to cover the full
  12-point matrix: deterministic ordering of several archived (id-tie included), bucket
  disjointness (current/retained/orphans/alreadyArchived partition the eligible set), current
  invariant under archived presence, mixed 4-bucket scenario, no-archived parity with pre-Stage-B
  semantics, archived-but-ineligible assets ignored entirely, and a behavioral pin on
  `defaultResolveVideoSource` (lifecycle plays no role in selection — the authority is untouched).
- **Stage C — Supabase `ArchiveWriter`** *(implemented 2026-07-25)*. The conditional UPDATE via the
  service client + the idempotent `activity_log` audit (F4.1 ensure-pattern). Migrations
  authored-not-applied: `archived_at` column + `archived_at` partial index + the `activity_log`
  archive partial-unique index (+ apply the pending `assets_listing_kind_source_idx`).
  Implementation notes:
